# Conga Field Usage Analyzer — standalone web application and Chrome extension

Version 0.8 runs the same app in two ways, from one codebase:

- **Standalone site** — a local Node.js server (`npm start`).
- **Chrome extension** — the same UI and scanners run inside a Chrome tab and call Conga Platform directly. No server is involved.

Both include searchable tenant metadata plus Formula Dependency, Workflow, Field Expression and Custom Code scans. There is no Conga TS Inspector integration.

## Run as a standalone site

Requires Node.js 20 or newer.

```bash
npm start
```

Open `http://localhost:4100`, enter an approved Conga Platform API URL, and paste a current bearer token.

## Run as a Chrome extension

```bash
npm run build:extension
```

This writes the extension to `dist/extension` (not committed). In Chrome, open `chrome://extensions`, turn on **Developer mode**, choose **Load unpacked** and select `dist/extension`. Click the purple circle in the toolbar to open the analyzer in its own tab. After pulling changes, run the build again and click **Reload** on the extension card.

- Extension pages may call Conga Platform directly, so no proxy server is needed. Access is limited to `*.congacloud.com`, `*.congacloud.eu` and `*.congacloud.au` (plus any approved gateway, below). The app's exact-host allowlist still applies on top of this.
- Scans run in the tab, not in the background service worker, so a long scan is not cut off when Chrome suspends an idle worker.
- The extension requests no `storage` permission. The token and results live only in the tab's memory; closing or reloading the tab clears them.
- `.env` settings (`CONGA_ALLOWED_PLATFORM_HOSTS` and the `CONGA_*_URL_TEMPLATE` link templates, including `CONGA_FIELD_EXPRESSION_URL_TEMPLATE`) are read **at build time** and written into `extension-config.js`. An approved gateway host is also added to the manifest's host permissions. Rebuild after changing `.env`.
- The icon is a solid circle in Conga Purple 300 (`#806CF0`, the app's accent colour). The PNG sizes are generated by the build; `public/icon.svg` is the favicon for both versions.

Distribution beyond your own browser (Chrome Web Store private listing or managed install by IT) needs Security/IT approval, because the extension handles tenant bearer tokens.

## One codebase, two runtimes — rules for every change

Every change must work in **both** the standalone site and the extension. The layout makes that the default:

| Path | Role | Runs in |
|---|---|---|
| `public/` | UI (`index.html`, `app.js`, `styles.css`, `icon.svg`) | both |
| `server/api.js` | The single API router (`/api/config`, `/api/platform/...`) | both |
| `server/*.js` except `index.js` | Conga client, URL policy, scanners, ZIP reader | both (copied to `core/` in the extension) |
| `server/index.js` | HTTP host for the standalone site only: static files and `api.handle()` | standalone |
| `extension/` | `manifest.base.json` and the toolbar `background.js` | extension |
| `scripts/build-extension.js` | Builds `dist/extension`, generates manifest, config and icons | build |

1. **Add or change API routes only in `server/api.js`.** `server/index.js` must stay a thin HTTP wrapper.
2. **Call the API from the UI only through `request()` in `public/app.js`.** It goes over HTTP on the standalone site and calls `server/api.js` in-page in the extension.
3. **Keep shared modules browser-safe:** no `node:` imports, `Buffer`, `fs` or direct `process` access. Use `Uint8Array`, `TextDecoder`, `DecompressionStream` and `fetch`, and read settings through options or `globalThis.process?.env ?? {}`.
4. **No persistent storage in either runtime:** no `localStorage`, `sessionStorage`, IndexedDB, cookies or `chrome.storage`.
5. **New Conga API host?** Add it to the allowlist in `server/platformUrl.js` and, if it is not under the existing domains, to `extension/manifest.base.json` (`host_permissions` and `connect-src`).
6. **Run `npm run check` before committing.** It syntax-checks, runs every test (including `test/extension.test.js`, which builds the extension and runs a full scan through the built `core/api.js`), and builds the extension. The build fails if a shared module uses a Node-only API or persistent storage.

## Search behavior

Object and field selection use searchable comboboxes rather than fixed dropdowns:

- **Objects:** searched by label or API name and displayed as `Object Label - API name`.
- **Fields:** searched by label, API name, or data type and displayed as `Label - API name - Data type`.
- Object search follows every metadata page before filtering, so matches after the first 200 objects are included.
- Field search reads the complete `FieldMetadata` collection for the selected object before filtering, so matches after the first 200 fields are included.
- Up to 50 matching rows are returned to the browser per search, together with total match and total scanned counts.

Because persistent metadata storage is prohibited, each search re-reads the required live Platform metadata. Rapid UI input is debounced and stale responses are ignored.

## Usage scan

**Find usage** runs four request-scoped collectors:

1. **Formula dependencies**
   - Shows what the selected field depends on when it is a formula.
   - Finds formula fields in the selected object's full schema whose `ExpressionDependency` references the selected field.
   - Calls the Platform dependency-fields metadata endpoint and merges additional dependent-field results without duplicates.
2. **Workflow references**
   - Pages through `POST /api/workflow/v1/query/WorkflowDefinition?IncludeTotalCount=true` (`IsLatest=true`, all workflow types).
   - Reads each definition from `GET /api/workflow/v1/workflow-definitions/{definitionId}/Latest`, five at a time.
   - Checks every activity property expression (Liquid, Literal, Json, …) plus variables and custom attributes:
     - `Object.Field` anywhere → **Exact**.
     - A Json `Key`/`FieldName` equal to the field, in a workflow on the selected object updating its context object → **Exact** (e.g. `FieldsToUpdate`).
     - The bare field name as a whole word, in a workflow on the selected object → **Probable**.
   - Usage is labelled Condition, Field update, Field mapping, Expression or Variable from the property name.
   - If the workflow API is unavailable, or a definition cannot be read, the collector reports `failed`/`partial` in limitations; the other collectors still return.

3. **Field expression references** (CPQ Field Expressions)
   - Pages through `POST /api/search/v1/objects/FieldExpression/query?includeTotalCount=true` selecting only `Id` and `Name`, sorted by `Id` (unique, so `Skip` paging cannot repeat or miss rows that share a `ModifiedDate`). The response is a bare array; rows are de-duplicated by `Id`.
   - Reads each expression from `GET /api/revenue-admin/v1/field-expressions/{id}`, five at a time.
   - Checks only the reference-bearing properties of the detail:
     - `UpdateField` — a path from `UpdateObject` (`Quantity`, `AttributeValue.Battery_Capacity_c`) → **Field update**.
     - `ConditionExpression` → **Condition**; `Expression` → **Value expression**. `$.Path` is a path from `SourceObject`; quoted literals (`'25 Mbps'`) are ignored.
     - `GroupByField`, `ParentField` — paths from `SourceObject`.
   - Relationship segments such as `AttributeValue.` are followed through lookup fields in the tenant schemas (the same resolution the formula collector uses):
     - Path resolves to the selected object (or names it explicitly, `Object.Field`) → **Exact**.
     - A relationship that cannot be resolved, a bare name without `$.`, or an `UpdateField` that is a display label (e.g. `Currency Attribute`) matching the field label → **Probable**, with a note.
   - Record metadata (`Name`, `CreatedBy`, `ModifiedBy`, `ETag`, …), `ConditionScope`, `EvaluationContext` and `Product`/`ProductGroup` names are context only, never matches.
   - One row per expression with columns **Field expression name** (linked), **Is active**, **Expression type**, **Used in** (Update field, Filter expression, Update expression, Group by field or Parent field — coloured green for exact, orange for probable, with a legend; hover shows any note) and **Matching expression** (the matching text, one line per match). Blank values stay blank.
   - Results link to the CPQ admin page (`{platformUrl}/cadmin/field-expression/{id}` by default). The section is shown above **Custom code**.
   - If the API is unavailable (for example a tenant without CPQ), or an expression cannot be read, the collector reports `failed`/`partial`; the other collectors still return.

   - **Product attributes.** Attributes are `Attribute` records (data), not schema fields. The object search offers a **Product Attributes** entry (for an empty query or one matching "attribute"/"product attributes"); its field search lists every attribute from `POST /api/search/v1/objects/Attribute/query?includeTotalCount=true` (`Id`, `Name`, `DisplayName`, `Type`; paged by `Id`) as `Display Name - API Name - Type`.
     - An attribute scan checks Field Expressions, workflows and custom code on the attribute API name. In Field Expressions, `Attribute.<Name>` and `AttributeValue.<Name>` (the same thing; `$.` optional) in Update field, Filter expression or Update expression → green. `__c` and `_c` endings are treated as the same.
     - The attribute's display name as `UpdateField` (e.g. `Currency Attribute`), or the bare name without the `Attribute.` prefix → orange.
     - Workflows: `Attribute.<Name>` / `AttributeValue.<Name>` anywhere → **Exact**; a Json `Key`/`FieldName` or the bare API name as a whole word, in any workflow → **Probable**.
     - Custom code: a string `"Attribute.<Name>"` / `"AttributeValue.<Name>"` → **Exact**; a string equal to the API name (e.g. `GetAttribute("Internet_Speed_c")`) → **Probable**; the name inside a longer string or as an identifier → **Possible**. "Runs as" is unchanged.
     - Formula dependencies are not applicable (shown in Scan coverage).
     - In a normal field scan, `Attribute.X` / `AttributeValue.X` paths are never matched unless a real lookup with that name resolves to the selected object.

4. **Constraint rule references** (CPQ Constraint Rules)
   - Pages through `POST /api/search/v1/objects/ConstraintRule/query?includeTotalCount=true` selecting `Id`, `Name`, `Type`, `IsActive` (sorted by `Id`).
   - For each rule (five at a time) reads `GET /api/revenue-admin/v1/constraint-rules/{id}/conditions?sort=asc(Sequence)` and `GET /api/revenue-admin/v1/constraint-rules/{id}/actions`.
   - Conditions: `ConditionCriteria` (a JSON string) is parsed; every predicate `FieldName` is matched against the field with its `ObjectName` (green when it is the selected object; a right-hand-side field reference is orange). `ProductFieldA`–`D` are Product fields. Actions: `ActionCriteria` (same format) and `ActionExpression` (`Object.Field` green, bare name orange).
   - Product attributes: a predicate on an attribute object (e.g. `LineItemAttributeValue`) or `Attribute.`/`AttributeValue.` paths → green; the bare attribute name on another object → orange.
   - Picklist options, `exprStr`, `Message`, names and audit fields are never matches; `exprStr` is shown as the readable summary.
   - Section below **Field expressions**: Constraint rule name (linked to `{platformUrl}/cadmin/constraint-rules/edit/{id}`, override with `CONGA_CONSTRAINT_RULE_URL_TEMPLATE`), Is active, Type, Used in condition, Used in action (matching condition/action names, coloured green/orange, with their criteria).
   - A rule whose conditions or actions cannot be read marks the collector `partial`; a failing list call marks only this collector `failed`.

5. **Attribute-based constraint rule references** (CPQ, product attribute scans only)
   - Pages through `POST /api/search/v1/objects/AttributeConstraintRule/query?includeTotalCount=true` selecting `Id`, `Name`, `RuleType`, `IsActive` (sorted by `Id`).
   - For each rule (five at a time) reads `GET /api/revenue-admin/v1/attribute-constraint-rules/{id}/entries`.
   - Each entry's `ConditionAttributes[].Name` is matched on the attribute API name (`__c`/`_c` treated as the same; `Attribute.`/`AttributeValue.` prefix allowed) → green, shown as `Name Operator Value`.
   - Condition values, the action side (`ActionProduct`, `ActionIntent`, `TargetFields`), names and audit fields are not matched.
   - Section below **Constraint rules** (shown for product attribute scans; normal field scans do not call these APIs): rule name (linked to `{platformUrl}/cadmin/attribute-based-constraint-rules/edit/{id}`, override with `CONGA_ATTRIBUTE_CONSTRAINT_RULE_URL_TEMPLATE`), Is active, Type (`RuleType`), Used in condition.
   - A rule whose entries cannot be read marks the collector `partial`; a failing list call marks only this collector `failed`.

6. **Custom code references**
   - Lists every project with `GET /api/extensibility/v1/customcode`.
   - Reads each project's source from `GET /api/extensibility/v1/customcode/{name}` (`Documents[].SourceCode`), three at a time. If a project returns no documents, it falls back to `GET /api/extensibility/v1/customcode/{name}/download` and reads the `.cs`/text files from the ZIP in memory (`bin/` and `obj/` are skipped).
   - Works out how each class runs, shown as **Runs as**:
     - Service Hook rules (`GET /api/extensibility/v1/servicehooks/rules`, all pages) → `CustomCodeDetails.ProjectName/ClassName`.
     - Callbacks → `GET /api/extensibility/v1/callbacks/modules/Revenue` → `CustomCodeMapping.ProjectName/ClassName`. Shown in the **Callback** column (callback short name, full name on hover; blank when none) with a **Callback** filter including "(No callback)"; "Runs as" keeps Service Hooks and Custom APIs.
     - Custom APIs → `GET /api/extensibility/v1/customcode/api-resource` and `.../{resource}/uri-entries` → `CustomCodeName`, `FullyQualifiedClassName`, `MethodName`.
   - Analyses C# as text. Comments are ignored, and string literals and identifiers are matched as whole tokens:
     - `"Object.Field"` inside a string → **Exact**.
     - `"Field"` as a whole string literal, in a file that names the object or a class wired to a hook on the object → **Exact**; when only another file in the project names the object → **Probable**; otherwise → **Possible**.
     - The field inside a longer string (criteria, select lists) → **Probable** when the object is in context, otherwise **Possible**.
     - `record.Field` style identifiers → **Probable**, reported only when the object is in context.
   - Labels each match **Write** (`rec["F"] = …`, `Set*("F", …)`, `{ "F", v }` in an insert/update dictionary, `obj.F = …`), **Read** (`rec["F"]`, `Get*("F")`, `obj.F`), **Query / criteria**, **Declaration** or **Reference**, with file, line, class and method.
   - If Service Hook, callback or Custom API mappings cannot be read, matches are still reported and the `limitations` array in the API response says "Runs as" may be incomplete. If the custom code API is unavailable, the collector reports `failed` and the other collectors still return.

Service Hooks have no section of their own. The code a hook runs is scanned under **Custom code**, and **Runs as** names the hook. A hook on the selected object whose configured condition names the field (`Object.Field` or `Field` as a whole token) is also listed under **Custom code** with access **Condition** and confidence **Exact**, showing the condition, the hook and the project/class it runs.

The **Custom code** section has a search box and two drop-down filters: **Project** (each project with its row count; Service Hook conditions with no project appear as *(No project)*) and **Access** (Read, Write, Condition and any other access value in the results). Filters and search combine: a row is shown only when it matches the selected project, the selected access and every search word (project, file, class, method, access, confidence, Runs as or code). **Clear filters** resets them. Filtering only changes what is shown; it does not call the tenant again and nothing is saved.

The results show **Scan coverage** (status and match count per collector) but no limitations list. A collector that could not finish shows `partial` or `failed` there. The `limitations` array is still returned by `POST /api/platform/usage-scan` for anyone calling the API directly.

## No persistent storage

No bearer token, tenant metadata, scan definition, or scan result is persistently stored:

- No server sessions, cookies, files, database records, Redis, or application cache.
- No localStorage, sessionStorage, IndexedDB, cookies, or Service Worker cache.
- Every API operation requires Platform URL and bearer token again.
- The browser retains the active connection and rendered results only in current-page runtime memory.
- Disconnect, reload, navigation, or tab close clears that runtime state.
- Responses and browser fetches use `Cache-Control: no-store` / `cache: no-store`.

Transient request memory necessarily exists while executing a request; the backend keeps no reference after responding.

## Platform URL policy

The URL must use HTTPS, contain only an origin, use the standard HTTPS port, and match an approved Conga host. Paths, queries, fragments, embedded credentials, arbitrary hosts, localhost, IP literals, and lookalike suffixes are rejected before outbound access. Redirects are disabled.

Built-in production origins:

- `https://rls.congacloud.com`
- `https://rls.congacloud.eu`
- `https://rls.congacloud.au`

An approved exact private-gateway hostname can be added with:

```bash
CONGA_ALLOWED_PLATFORM_HOSTS=approved-gateway.example.internal
```

Wildcards are not supported.

## Reference links

Usage-scan results show the record **ID** returned by the Platform API and, when a URL template is configured, link the result name to its page in the Conga admin UI (opens in a new tab). Set the templates in `.env` (loaded automatically on Node 20.12+) or the shell:

```bash
CONGA_FIELD_URL_TEMPLATE={platformUrl}/path/to/objects/{objectName}/fields/{fieldName}
CONGA_WORKFLOW_URL_TEMPLATE={platformUrl}/workflow/{id}/   # default when unset
CONGA_FIELD_EXPRESSION_URL_TEMPLATE={platformUrl}/cadmin/field-expression/{id}   # default when unset
CONGA_CUSTOM_CODE_URL_TEMPLATE={platformUrl}/path/to/custom-code/{name}   # {name} = project name
```

Placeholders: `{platformUrl}` (the connected tenant origin), `{id}`, `{objectName}`, `{fieldName}`, `{name}`. Values are URL-encoded. If a placeholder has no value for a result (for example the API returned no `Id`), that result is shown as plain text instead of a broken link. Copy the address of a real record page in your tenant to get the exact path.

## Verify

```bash
npm run check
```

`test/extension.test.js` builds the extension into a temporary folder, checks the manifest, icons and browser safety, and runs validate, field search and a full usage scan (including the ZIP fallback) through the extension's copy of the core.

The integration suite uses a local mock tenant containing 251 objects, 251 fields, and 202 Service Hooks to prove search and scanning continue beyond 200 without calling a real tenant. `test/customCode.test.js` adds a mock tenant with custom code projects (inline documents, a ZIP-only project, an unreadable project), a Service Hook, a callback mapping and a Custom API route.

## Current boundary

Custom code is matched as text, not compiled, so field names built at runtime (string concatenation, constants defined in another project, generic loops over every field) are not detected. Read and write access is inferred from common Platform patterns, so review Probable and Possible matches. Data written through external REST API calls, imports and integrations is not visible to any collector. A tenant-wide asynchronous index would require approved encrypted job storage; this no-storage build instead performs synchronous, request-scoped scans, and source code is held only in request memory.
